# 源码阅读指南

这个仓库的运行链很短。建议先看数据，再看状态逻辑，最后看页面如何调用接口。

## 1. 从合成样例开始

先读 [`samples.py`](../samples.py)。它定义了六条独立编写的合成会话，覆盖五类服务：

- 选品咨询；
- 不良反应；
- 售后退货；
- 补发换货；
- 订单款项。

每条会话包含消息、三类证据、待核对缺口、候选草稿和风险等级。`DEMO-006` 多一条后续消息，用于观察按消息时点回放时，未来证据如何被排除。

阅读时先留意 `seq` 与 `available_seq`。前者决定消息出现的顺序，后者决定证据从哪个时点开始可见。这里没有竞赛原始数据、真实消费者记录或品牌资产。

## 2. 阅读核心状态逻辑

接着读 [`core.py`](../core.py)，重点看 `Store` 的三个公开行为。

### `analyze()`

`analyze()` 根据 `sid` 找到样例，再按 `upto_seq` 截取消息和证据。函数内部的 `step()` 依次记录六步 Trace。最终返回的主要字段包括：

- 当前可见的 `messages` 与 `evidence`；
- `service`、`risk` 和 `missing`；
- 可编辑的 `draft`；
- `verifier` 与高风险场景需要的 `required_checks`；
- `analysis_id`、`trace` 和明确的离线边界字段。

`analysis_id` 使用规范化 JSON 的 SHA-256 摘要生成。阅读 `context` 的组成可以看出，哈希绑定的是可见上下文，而不是临时耗时。

### `feedback()`

`feedback()` 处理人工决定。先看这几条分支：

- `decision == "adopt"`：核对高风险检查项、终稿内容和公开示例规则；
- 终稿与原草稿相同：记录 `adopt_as_is`；
- 终稿经过修改：记录 `adopt_edited`；
- `decision == "reject"`：记录 `rejected`。

再看幂等与上下文检查。请求键与请求体指纹一起存入 `requests` 表。同键同体返回原结果，同键异体冲突。`contexts` 表保存每个会话的最新分析；提交旧分析时会返回 `STALE_CONTEXT`。

### `summary()`

`summary()` 返回版本、合成与无执行标记、会话列表及最近的本地反馈摘要。它为页面初始化提供数据，不构成业务统计或效果指标。

## 3. 阅读本地服务入口

[`app.py`](../app.py) 使用 `ThreadingHTTPServer` 提供三个接口：

| 方法 | 路径 | 用途 |
| --- | --- | --- |
| GET | `/api/state` | 读取会话与本地反馈摘要 |
| POST | `/api/analyze` | 分析一个会话的指定消息时点 |
| POST | `/api/feedback` | 记录采纳、改写或拒绝 |

文件还负责静态资源、Host 与 Origin 检查、JSON 请求限制和错误映射。启动参数 `--port` 控制本地端口，`--db` 控制 SQLite 文件位置。服务明确绑定 `127.0.0.1`。

## 4. 沿前端交互阅读

前端由三个文件组成：

- [`web/index.html`](../web/index.html)：工作台结构、证据与 Trace 面板、人工草稿区；
- [`web/app.js`](../web/app.js)：加载会话、调用分析接口、管理消息时点、提交人工决定；
- [`web/styles.css`](../web/styles.css)：布局、状态样式和响应式规则。

阅读 `web/app.js` 时，可以按用户操作追踪：加载 `/api/state` → 选择会话 → 调用 `/api/analyze` → 修改或保留草稿 → 调用 `/api/feedback`。特别检查高风险核对、按钮禁用、幂等键和错误信息如何与后端约束对应。

## 5. 适合动手验证的路径

运行项目后，可以用界面检查以下行为：

1. 在 `DEMO-006` 中切换消息时点，比较证据与草稿；
2. 在普通样例中分别原样采纳、编辑后采纳和拒绝；
3. 在高风险样例中观察核对项对提交的限制；
4. 切换同一会话的消息时点后，确认旧上下文不会被继续采纳；
5. 检查界面是否始终把草稿、复制、本地记录和真实发送分开。

这份指南只覆盖当前仓库内实际存在的文件和行为。它不把原工程、混合快照或未公开模块写成可点击源码。
